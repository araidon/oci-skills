# 設計ポイント解説の出力形式

`.drawio` の生成・編集が終わったら、**必ず** 設計ポイントの解説をテキストで出力する。
図だけ渡しても、なぜその構成にしたのかが伝わらないため。

---

## 共通フォーマット

- 番号付きリストで主要ポイントを列挙する
- 各ポイントは **太字の見出し** + 説明文（2〜3文程度）
- 簡潔に、ただし具体的に（「冗長化しました」ではなく「App サーバーを3台に分け、
  Fault Domain をまたいで配置」）

---

## 自然言語からの新規作成時

以下の観点をカバーする。

1. **階層設計** — Region / VCN / Subnet をどう分割したか、その理由
2. **ネットワーク設計** — ゲートウェイ（IGW / NAT / DRG / SGW）の選定理由と接続パターン
3. **コンポーネント配置** — 各サービスの選定理由と役割
4. **セキュリティ設計** — Bastion / WAF / Vault などの採用理由
5. **可用性・冗長化** — 冗長構成、ロードバランサー、Data Guard などの設計判断

## AWS / Azure の構成図からの変換時

上記に加えて、以下を必ず含める。

### サービスマッピング表

Markdown の表で、元クラウド → OCI の対応を示す。
対応表は `reference/cloud-mapping.md` を根拠にする。

```markdown
| AWS | OCI | 備考 |
|---|---|---|
| VPC | VCN | |
| ALB | Load Balancer | L7。L4 なら Flexible Load Balancer |
| 踏み台EC2 | Bastion | マネージドサービスに置き換え |
```

### アーキテクチャパターンの変換

元の設計パターンが OCI でどう表現されるか。

- マルチアカウント → マルチコンパートメント
- Transit Gateway → DRG
- AZ ごとのサブネット → Regional Subnet + Fault Domain

### OCI 固有の最適化

マネージドサービスに置き換えた箇所とその理由。

- 踏み台 EC2 → OCI Bastion サービス
- サービスごとの VPC Endpoint → Service Gateway 1つ

### 差異・注意点

1:1 対応しないサービス、OCI 側で構成が変わる箇所を明示する。
「近似で置き換えた」ものは、そう書く。
